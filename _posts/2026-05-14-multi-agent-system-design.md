在复杂任务处理中，单一 Agent 往往很难同时兼顾全局规划、细节执行、工具调用、结果校验和任务协作。尤其当任务链路较长、涉及多个工具或需要多种专业能力时，如果所有逻辑都堆在一个 Agent 里，系统会变得臃肿、难维护，也容易出现执行混乱的问题。

因此，一个更清晰的设计方式是构建“主控 Agent + 分 Agent + Skill”的多 Agent 系统。主控 Agent 负责理解目标、拆解任务和协调流程；分 Agent 负责具体子任务；Skill 则像操作手册一样，告诉分 Agent 应该如何完成某类任务、调用哪些 MCP 或工具、按照什么步骤执行。

## 一、整体架构：主控 Agent 负责统筹，分 Agent 负责执行

多 Agent 系统的核心思想，是把复杂任务拆成多个可管理、可复用、可协作的小任务。系统中最上层是主控 Agent，它不直接承担所有细节工作，而是更像一个项目经理或调度中心。

主控 Agent 的职责主要包括：

1. 理解用户的最终目标。
2. 判断任务需要哪些能力。
3. 将大任务拆分成多个子任务。
4. 设计 Agent 调度工作流，明确每个分 Agent 的执行顺序、依赖关系和交付结果。
5. 为每个子任务分配合适的分 Agent。
6. 跟踪各个分 Agent 的执行进度。
7. 汇总结果，并进行最终判断、整合和输出。

在这个模式下，主控 Agent 不需要对所有领域都“亲自下场”。它最重要的能力不是做每一件事，而是知道应该让谁做、什么时候做、做到什么程度、结果如何验收。

这里还需要特别注意一点：主控 Agent 在正式调度分 Agent 之前，应该先设计一份清晰的工作流。这个工作流要写明先调用哪个 Agent、后调用哪个 Agent、哪些任务可以并行、哪些任务必须等待前置结果完成。这样做的目的，是防止主控 Agent 在复杂任务中遗漏某个分 Agent，或者因为调度顺序不清晰导致重复执行、漏执行和结果无法衔接。

## 二、分 Agent：一个 Agent 负责一类具体事情

分 Agent 是系统中的执行单元。设计分 Agent 时，原则应该是“一个 Agent 负责一个事情”，并且职责描述越清晰、越详细越好。

例如，一个复杂的软件开发任务可以拆成多个分 Agent：

1. 需求分析 Agent：负责理解需求、梳理功能边界和输出任务清单。
2. 架构设计 Agent：负责设计模块关系、数据流和技术方案。
3. 编码 Agent：负责根据设计修改代码或实现功能。
4. 测试 Agent：负责编写测试、运行测试并定位失败原因。
5. 文档 Agent：负责整理使用说明、接口说明或项目文档。
6. 审查 Agent：负责检查代码质量、潜在风险和遗漏点。

这样做的好处是，每个分 Agent 的职责边界都很明确，不会互相抢任务，也不会因为目标过大而执行发散。主控 Agent 只需要把合适的任务交给合适的分 Agent，再根据结果进行协调即可。

分 Agent 的描述应该尽量具体，不能只写“你负责测试”这种笼统指令，而应该写清楚它的工作范围、判断标准、可调用工具、输出格式和异常处理方式。描述越具体，Agent 的行为就越稳定，系统整体也越容易复用和扩展。

## 三、Skill：把经验写成可复用的执行手册

如果说分 Agent 解决的是“谁来做”的问题，那么 Skill 解决的就是“具体怎么做”的问题。

Skill 可以理解为某类任务的操作手册，它详细描述了完成任务时应该遵循的步骤、可以调用的工具、可使用的 MCP、输入输出格式以及注意事项。分 Agent 在执行任务时，可以根据任务类型加载对应的 Skill，从而获得更具体的执行能力。

例如，一个“代码审查 Skill”可以包含：

1. 先读取相关代码文件。
2. 查看最近的修改记录。
3. 判断是否存在逻辑错误、边界条件遗漏、性能问题或安全风险。
4. 必要时运行测试或静态检查工具。
5. 输出审查结果时按严重程度排序。
6. 如果没有发现问题，也要说明测试覆盖和剩余风险。

再比如，一个“网页自动化 Skill”可以写明：

1. 什么时候应该打开浏览器。
2. 如何访问本地页面或线上页面。
3. 如何点击、输入、截图和验证页面状态。
4. 如果页面加载失败，应该如何排查。
5. 最终需要返回哪些观察结果。

通过 Skill，系统可以把隐性的操作经验显性化，把一次性的执行方式沉淀成可复用能力。这样不仅能减少重复提示词，也能让不同分 Agent 在处理同类任务时保持一致的行为标准。

## 四、MCP 和工具调用：让 Agent 具备真实操作能力

在多 Agent 系统中，Agent 不能只停留在“文本推理”层面。很多任务需要访问文件、运行命令、查询数据库、调用浏览器、读取外部系统或操作某些专业软件。这时就需要通过 MCP 和工具调用，为 Agent 提供真实的操作能力。

Skill 中应该明确写出：

1. 当前任务需要调用哪些 MCP 或工具。
2. 每个工具在什么情况下使用。
3. 调用工具前需要准备什么信息。
4. 调用工具后如何解析结果。
5. 如果工具调用失败，应该如何重试或降级处理。

例如，文件分析 Agent 可以使用文件读取工具和搜索工具；浏览器测试 Agent 可以使用浏览器 MCP；逆向分析 Agent 可以使用 IDA MCP；数据处理 Agent 可以使用表格、脚本或数据库相关工具。

这种设计的关键是让工具调用变得可控，而不是让 Agent 随意尝试。工具越多，越需要通过 Skill 进行约束。否则 Agent 可能会调用不合适的工具，或者在没有必要的时候执行高成本操作。

## 五、推荐的执行流程

一个完整的多 Agent 系统可以按照以下流程运行：

1. 用户提出目标。
2. 主控 Agent 理解目标，并判断任务复杂度。
3. 主控 Agent 将任务拆分为多个子任务。
4. 主控 Agent 先设计 Agent 调度工作流，确定调用顺序、并行关系、依赖关系和验收节点。
5. 主控 Agent 为每个子任务选择合适的分 Agent。
6. 分 Agent 根据任务类型加载对应 Skill。
7. Skill 指导分 Agent 调用 MCP、工具或执行具体操作。
8. 分 Agent 返回阶段性结果。
9. 主控 Agent 按照工作流检查每个节点是否完成，防止遗漏调度。
10. 如有遗漏，主控 Agent 继续派发补充任务。
11. 所有结果完成后，主控 Agent 统一整合并输出最终答案。

这个流程的重点是形成闭环：不是简单地把任务丢给分 Agent，而是要有拆解、执行、反馈、校验和整合。只有形成闭环，多 Agent 系统才不会变成多个 Agent 各说各话。

## 六、设计分 Agent 和 Skill 时的关键原则

第一，职责要单一。每个分 Agent 最好只负责一类事情，避免一个 Agent 同时承担太多角色。

第二，描述要详细。Agent 的角色说明、任务边界、工具权限、输出格式和判断标准都应该写清楚。

第三，Skill 要可执行。Skill 不能只是理念描述，而应该像流程手册一样，明确到“先做什么、再做什么、什么情况下调用什么工具”。

第四，工具调用要有边界。能不用工具时不要乱用工具，必须用工具时要明确使用目的和结果处理方式。

第五，主控 Agent 要负责验收。分 Agent 产出的结果不应该直接作为最终结果，而应该由主控 Agent 统一检查、整合和修正。

第六，系统要方便扩展。后续如果出现新的任务类型，只需要新增分 Agent 或新增 Skill，而不必重写整个系统。

## 七、这个设计的价值

这种设计方式最大的价值，是让 Agent 系统从“单个智能体完成所有事情”升级为“多个专业角色协同完成复杂任务”。它更接近真实团队的工作方式：有人负责规划，有人负责执行，有人负责测试，有人负责审查，有人负责整理结果。

同时，Skill 的存在让系统具备可沉淀、可复制、可优化的能力。每当某类任务被执行得更好，就可以把经验写进 Skill 中，让后续 Agent 继续复用。随着 Skill 越来越完善，整个系统会逐渐从“依赖临场发挥”变成“依赖稳定流程”。

最终，一个成熟的多 Agent 系统应该具备三个特点：主控清晰、分工明确、执行可控。主控 Agent 负责方向和协调，分 Agent 负责专业任务，Skill 负责具体方法，MCP 和工具负责真实操作。四者结合起来，就能形成一个既灵活又稳定的智能协作系统。

## 八、总结

多 Agent 系统的关键不在于 Agent 数量越多越好，而在于结构是否清晰、职责是否明确、流程是否闭环。主控 Agent 是大脑，分 Agent 是执行团队，Skill 是操作手册，MCP 和工具是实际能力。

如果要继续完善这个系统，可以从三个方向入手：第一，设计主控 Agent 的任务拆解规则；第二，为常见任务创建标准化分 Agent；第三，把高频操作沉淀成 Skill，并明确每个 Skill 应该调用哪些 MCP 和工具。

当这些部分逐渐完善后，多 Agent 系统就不只是一个概念，而会变成一个能够稳定处理复杂任务、持续积累经验、不断扩展能力的协作框架。
